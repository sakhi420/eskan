# اولویت‌بندی MVP — نسخهٔ پس از بازبینی دامنه

- **تاریخ:** 2026-11-04
- **اصل:** همهٔ قابلیت‌ها P0 نمی‌شوند. هدف: مدیر لیلیهٔ کوچک/متوسط روزمره‌اش را بدون دفترچه/اکسل و محاسبات دستی مدیریت کند؛ حتی بدون اینترنت.

## سطح‌بندی

- **P0:** هستهٔ قابل‌فروش اقامت — باید در MVP باشد.
- **P1:** مهم برای مدیریت بهتر، قابل افزودن بعد از MVP (اما طراحی پایه از ابتدا).
- **P2:** تخصصی/آینده.

## P0 — هستهٔ اقامت و مالی

| ماژول | گنجانده می‌شود |
|---|---|
| لیلیه/اتاق/تخت | اطلاعات پایه + تماس + تنطیمات عملیاتی + وضعیت استفاده |
| ساکن | پروندهٔ پایه + تماس اضطراری؛ بدون الزام موبایل هوشمند؛ تلفن غیریکتا |
| پذیرش/قرارداد/تخصیص/خروج | جریان پذیرش، قرارداد + بستهٔ اقامت، تخصیص overlap-safe، تمدید، انتقال، Check-out |
| مالی | کرایهٔ ماهانه idempotent، پرداخت نقدی/دستی + پرداخت‌کنندهٔ جدا، ودیعه، مصارف، بدهی، رسید، Credit/Adjustment، گزارش بدهکاران |
| گزارش/رسید/صندوق ساده | dashboard، بدهی، خلاصهٔ مالی، statement، رسید |
| کاربران/نقش‌ها/همگام‌سازی | OWNER/ADMIN/OPERATOR/VIEWER + Offline-first + Backup/Restore |

## P1 — طراحی از ابتدا، اجرا بعد از هسته

- وضعیت نگهداری اتاق/تخت + درخواست تعمیر/نظافت.
- تخفیف.
- خروجی Excel/PDF.
- بستن صندوق روزانه.
- شکایت/درخواست ساکن.

## P2 — تخصصی/آینده

- ساختمان/بلوک (اختیاری برای مجموعه‌های بزرگ).
- غذا/آشپزخانه، انبار مواد غذایی، حقوق کارمندان.
- مهمان/مرخصی (در صورت سیاست لیلیه).
- درگاه پرداخت آنلاین، اتصال بانک/کیف پول، بیومتریک، هوشمند، AI.

## خارج از MVP (تأیید مجدد)

حسابداری دوطرفه، اپ ساکن، پنل وب، چند ارز، microservices/Redis، پرداخت آنلاین، پیامک/OTP، تحلیل پیشرفته.

## منطق تصمیم

1. **پول نقد و ثبت دستی** اساس است (طبق شواهد بانک جهانی).
2. **Offline-first** بدون وابستگی به اینترنت/برق دائمی.
3. **بستهٔ اقامت و غیابت موقت** باید از ابتدای فاز مالی درست طراحی شوند (تأثیر مستقیم بر قرارداد/کرایه/صورتحساب/حساب).
4. تعمیر/نظافت P1 است، اما مدل وضعیت اتاق/تخت باید از همین ابتدا طوری باشد که بعداً بازنویسی نشود.
